# Reproducible four-container Vision pipeline

## Run from a clean checkout

Prerequisites: Docker Desktop/Engine with Compose v2+, Python 3.9+ and make on the host.
Allow about 8 GiB of Docker memory for the sequential CPU jobs and app. No host research
environment or host ML library is required by the launcher. First-time image builds and
artifact downloads take longer; subsequent runs reuse images and verified source caches.

GCS ingestion requires your own authorized Application Default Credentials and read
access to the private `ac215-greenpath` bucket in project `organic-victory-508017-v9`.
The default ADC location is `~/.config/gcloud/application_default_credentials.json`.
Set `ADC_FILE` to a different authorized file if needed. Credentials stay outside Git
and images, and are mounted read-only only into the ingestion job.

From the repository root:

```sh
make run
```

This builds and runs four real ML containers, validates their outputs, starts API and
frontend containers, then issues a sample API request to verify the app serves that run.

- Frontend: http://localhost:3030
- API documentation: http://localhost:9030/docs
- Each invocation gets a unique run ID. Outputs are never silently overwritten.
- Current successful run pointer: `.artifacts/pipeline/latest.json`.

For an explicit run ID or different ports:

```sh
make run PIPELINE_ARGS="--run-id my-demo-001 --api-port 9003 --frontend-port 3003"
```

For ML jobs only:

```sh
make run PIPELINE_ARGS="--no-app"
```

After a successful online run has populated the verified caches:

```sh
make run PIPELINE_ARGS="--offline --no-build"
```

Offline mode performs actual preparation, image encoding, fitting and prediction again;
it only reuses immutable upstream inputs and weights. It does not copy previous model
outputs. `--no-build` requires already-built images matching the current code.

## Scope and the cached-data boundary

This pipeline starts from already-collected notebook 01-04 products: selected street-view
metadata, NAIP aerial images, OSM features and teacher labels. It performs real notebook
05 joins, filtering, H3 spatial splitting, a one-ring test buffer and grouped folds.
The encoder then performs actual crop/normalization/eight-view CLIP feature extraction.

It does not reacquire Mapillary data, recrop geospatial source rasters, recompute OSM
features or invoke paid teacher labeling on each run. The original collection/labeling
notebooks remain the upstream research implementation. The frozen snapshot is the explicit
starting input, not a claim that every external-source notebook has been containerized.

The current processed cells/OSM hashes differ from the historical v1 manifest. They are
published under a new source version with that audit recorded. Historical v1, its trained
M1 artifact and held-out evaluation remain unchanged.

## Execution order and artifacts

```text
data-processor container
  GCS snapshots -> checked source cache -> image extraction -> joins/filter/splits
        |
        v
feature-encoder container
  actual images -> 224 crop / CLIP normalization / eight views -> embeddings
        |
        v
model-training container
  fitting rows -> StandardScaler -> independent Ridge heads -> numeric model export
        |
        v
model-deploy container
  reload exported model -> predict -> align IDs and H3 geometry -> serving bundle
        |
        v
API + frontend
  user's text -> supported preference weights -> geographic matching heatmap
```

Compose dependencies use `service_completed_successfully`. A failed job blocks downstream
jobs. The three compute jobs have networking disabled. They receive no GCS credentials.
The ingestion cache is writable only to the ingestion job; compute jobs mount it read-only.
Per-run artifact directories are shared for job outputs and verified before app startup.

The API reads predictions generated by this run. It does not rerun CLIP per user request.
Changing preference weights only recomputes matching scores. Preference parsing defaults
to an English offline keyword parser; this is independent of the real visual model.

## Smoke versus full mode

Default smoke mode selects **32 train + 8 validation + 8 test = 48 cells**, after applying
the full spatial split and buffer. It fits on 40 cells, evaluates 8, then predicts all 48
for the application. This is a small, reproducible execution example, not a new benchmark
or a replacement for the historical 188-cell test report.

```sh
make run PIPELINE_MODE=full
```

Full mode retains all qualifying cells: the current input preparation produced 651 train,
173 validation and 188 test cells. Full image encoding takes longer. These are dataset
coverage cells, not all Boston geography. Consult evidence for which mode was actually
executed; the full preparation counts alone do not prove a completed full-mode run.

No parameter search is repeated. New pipeline training uses the prior encoder/alpha
selection with `--reference-policy none`, while independently checking export/reload
agreement and preserving train/test separation. Historical reproduction commands from
STEP2 retain their stricter comparison against old predictions.

```text
│   ├── logs/           # build, ML and app startup output

│   ├── sample-request.json
│   ├── sample-response.json
│   └── run-summary.json
└── latest.json
```

The launcher checks all five artifact manifests, dataset counts and model identities.
It then checks API response IDs/count/model version and frontend HTTP readiness. A failed
run records its error but does not replace the pointer to the last successful run.
The source-code hashes in the run summary identify the implementation used at execution.

Hashes detect inconsistency with a manifest; they are not digital signatures. Inputs
are expected from the team's authorized bucket and trusted checkout.

## Tests, evidence and cleanup

```sh
make pipeline-test
make test
```

`pipeline-test` covers model/training, image preprocessing, data preparation, unsafe
archives, model/region alignment and launcher parsing. `make test` checks the API.
Real Docker/GCS/browser evidence is retained under `docs/pipeline/evidence/`, separately
from unit tests. Full execution logs and complete responses remain in each local run.

The four ML containers exit after success and remain available for inspection. The two
app containers continue running. To stop the app:

```sh
docker compose -p greenpath-pipeline-app down
```

To inspect a particular ML run:

```sh
docker ps -a --filter label=com.docker.compose.project=gp-ml-RUN-ID
```

After inspecting, remove that run's stopped containers using their explicit names in
Docker Desktop or `docker rm`. Do not remove original data or shared caches to stop jobs.

## Verified execution

Run `smoke-20261018-02` completed the online GCS ingestion, four ML jobs and local app
verification in 92.57 seconds with cached Docker builds. It freshly encoded 48 images,
fit on 32 training plus 8 validation rows, and evaluated on 8 held-out test rows. Reloading
in a fresh process reproduced predictions within 5.97e-8. All four jobs exited with code 0.

The API served this newly trained model, and a real browser verified the preference input,
heatmap and model/source indicators. See `evidence/run-summary.json`, `evidence/pipeline-ml.log`,
`evidence/ml-containers.json` and `evidence/ui-preview.jpg`. The test suites passed 45 ML/data/
launcher checks and 59 API checks (104 total). Full-mode preparation was verified at
651/173/188 rows; full-mode image encoding and training were not executed in this delivery.
